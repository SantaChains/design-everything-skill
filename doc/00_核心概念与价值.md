## 一、Skill 的本质定义

### 1.1 核心定义

**Skill = 能力封装单元**

Skill 是一份清晰、严谨、可执行的指令文档,用于明确告诉模型:
- **When** (何时): 在什么条件下使用
- **How** (如何): 按照哪些步骤执行  
- **What** (什么): 产出什么结果

**本质**: Skill 是教 AI 按固定流程做事的操作说明书,一旦写好,就能像函数一样反复调用。它把"某类事情应该怎么专业做"封装成一个可复用、可自动触发的能力模块。

### 1.2 最小形态

一个 skill 最少只需要一个文件:

```
my-skill/
└── SKILL.md
```

`SKILL.md` 的结构很简单——上半部分告诉 AI"什么时候用我",下半部分告诉 AI"具体怎么做":

```yaml
---
name: my-skill                    # ← 上半部分:元数据
description: >-                   #    AI 靠这里决定要不要激活这个技能
  当用户需要做某件事时,使用这个技能。
---

下半部分:操作指令                   # ← AI 激活技能后才会读到这里
按照以下步骤执行...
```

### 1.3 完整结构

当一个技能变复杂时,单靠一个 SKILL.md 就不够了:

```
skill-name/
├── SKILL.md                  # [必需] 入口文件:frontmatter + body
├── agents/
│   └── openai.yaml           # [推荐] 技能的"名片"
├── scripts/                  # [可选] 可执行脚本
├── references/               # [可选] 参考文档
└── assets/                   # [可选] 产出物模板
```

**各组件职责**:
- **SKILL.md** — 唯一必需的文件,包含触发条件和操作指令
- **scripts/** — 写好的程序,AI 不需要读懂它,直接调用 shell 执行
- **references/** — AI 在工作过程中需要查阅的参考资料
- **assets/** — 不是给 AI 看的,而是直接用在最终产出里的文件
- **agents/openai.yaml** — 技能的"名片",给产品界面用的元数据

## 二、Skill 与其他概念的本质区别

### 2.1 Skill vs Prompt vs Command vs MCP

| 对比项 | 普通 Prompt | Skills 机制 | Command | MCP |
|--------|------------|------------|---------|-----|
| 每次都要重新描述 | 是 | 否(只描述一次) | 否 | 否 |
| 上下文长度占用 | 每次全量塞入 | 渐进式加载 | 固定 | 启动时加载 |
| 一致性 | 依赖每次 prompt 质量 | 高(固定 SOP + 模板) | 中 | 高 |
| 复用性 | 手动复制粘贴 | 自动匹配 / slash 命令 | 手动调用 | API调用 |
| 维护方式 | 改一次 prompt 就要重新发 | 修改 SKILL.md 文件,全局/项目生效 | 修改代码 | 修改配置 |

**关键区别**:
- **Prompt**: 一次性的对话指令
- **Command**: 常用的代码片段
- **Skill**: 一整套 SOP + 工具包
- **MCP**: 能力扩展(连接 API、数据库、外部工具)

### 2.2 Skill vs Agent vs Persona

| 类型 | 目的 | 范围 | 风格 |
|------|------|------|------|
| **Skill** | 如何执行任务 | 单一领域 | 中性 |
| **Agent** | 执行什么任务 | 单一领域 | 专业 |
| **Persona** | 谁在思考 | 跨领域 | 个性化 |

### 2.3 Skill vs 函数 vs API

| 维度 | 函数 | API | Skill |
|------|------|-----|-------|
| 调用方式 | 代码直接调用 | HTTP 请求 | 自然语言触发 |
| 触发条件 | 程序员决定 | 任何人访问 | AI 判断时机 |
| 上下文 | 局部变量 | 请求参数 | 对话历史 + 状态 |
| 容错性 | 低(需处理异常) | 中 | 高(AI 可追问澄清) |

## 三、Skill 的核心价值

### 3.1 关键价值

- **无需重训练**: 不修改模型权重即可扩展能力
- **模块化设计**: 易于测试、维护、复用
- **上下文优化**: 精确控制 token 消耗
- **可组合性**: 多个 Skill 协作完成复杂任务

### 3.2 性能提升

根据实际案例和学术研究:
- 任务准确率提升 40-70%(Liu et al., 2024)
- 开发周期缩短 60%(斯坦福 AI 指数报告, 2025)
- 首次解决率从 65% 提升至 92%(实际案例)

### 3.3 设计心法

把 AI 想象成刚毕业的聪明但没经验的实习生:

- **普通 Prompt** = 每次要从头教他怎么做事
- **Rule / 记忆** = 贴一张"公司行为守则"在工位上(一直生效,但只能管态度和格式)
- **MCP / Tools** = 给他电脑装了软件和 API(能调用外部工具,但不知道什么时候该用、怎么组合)
- **Skills** = 直接给他一整套"岗位培训大礼包"(PDF+流程图+SOP+话术模板+常用脚本),告诉他:"当老板让你做这类事情时,就按这个文件夹里的方法来做"

## 四、Skills vs MCP 边界

| Skills | MCP |
|--------|-----|
| 知识复用 | 能力扩展 |
| 经验、最佳实践、工作流程 | 连接 API、数据库、外部工具 |
| 基于 Markdown 文件,无需服务器 | 需要编码能力和服务器端配置 |
| 渐进式加载,Token 效率高 | 启动时加载全部工具定义 |
| 适用于 Web / Desktop / CLI | 更高的 Token 消耗与复杂度 |

## 五、触发方式

- **slash 命令**: 如 `/skill-name`
- **自动匹配**: 场景描述自动触发
- **项目共享**: 项目级别调用

## 六、常见认知误区

### 误区一: Skill 等同于一段 Prompt
❌ **错误**: Skill 并不是一次性的对话提示
✅ **正确**: Skill 是可长期复用、输入输出明确的能力模块,强调稳定、确定且易于工程化维护

### 误区二: Skill 是写给人看的文档
❌ **错误**: Skill 的目标不是解释原理
✅ **正确**: Skill 是下达指令,使用模型可解析的结构化语言,明确约束行为边界

### 误区三: Skill 越复杂越强大
❌ **错误**: 复杂度并不与能力强度挂钩
✅ **正确**: 职责单一、边界清晰的 Skill 更容易被正确触发并稳定执行

**重要提示**: 模型的上下文窗口是有限且宝贵的公共资源。每一个被加载的 Skill 都在竞争有限的上下文资源。因此,Skill 文档应以最小必要信息为目标,避免冗余解释与不必要的背景铺垫。
