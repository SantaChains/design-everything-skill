## 一、黄金法则(三大核心原则)

### 原则 1: 单职责优先(Single Responsibility)

**核心思想**: 每个 Skill 只做一件事,并把它做好

**反模式**:
```javascript
// ❌ "全能助手" —— 什么都能干
async function assistant(query) {
  if (query.includes('天气')) return getWeather();
  if (query.includes('新闻')) return getNews();
  if (query.includes('代码')) return reviewCode();
  // ... 还有 100 个 if
}
```

**最佳实践**:
```
// ✅ 拆成独立技能
weather-skill/
  SKILL.md    → 说明何时调用天气功能
  scripts/    → 只负责获取天气数据

news-skill/
  SKILL.md    → 说明何时调用新闻功能
  scripts/    → 只负责获取新闻数据
```

**好处**:
- 易于测试和维护
- 可以独立更新
- 便于复用和分享
- 降低上下文消耗

### 原则 2: 边界清晰(Clear Boundaries)

每个 Skill 必须有明确的**触发条件**和**退出条件**:

```markdown
## 🎯 触发条件(什么时候调用)

✅ 适合调用:
- 用户明确要求查询天气
- 对话涉及"明天穿什么""要不要带伞"
- 需要天气信息支持其他决策

❌ 不调用:
- 闲聊问候时
- 其他技能的子步骤中(除非明确需要)
- 用户只是提及"天气"一词但无查询意图
```

### 原则 3: 优雅降级(Graceful Degradation)

当主要功能不可用时,要有备选方案:

```python
async def getWeather(city):
    try:
        return await fetchFromPrimaryAPI(city)
    except error:
        console.warn('主 API 失败,尝试备用')
        
        # 备选方案 1:缓存数据
        cached = getCachedWeather(city)
        if cached:
            return { ...cached, fromCache: true }
        
        # 备选方案 2:友好提示
        return '抱歉,暂时无法获取天气信息,请稍后再试~'
```

## 二、Agent-Centric 设计原则

### 2.1 为工作流设计,而非 API 端点

**原则**: 设计高影响力的工作流工具,而非简单包装 API

**为什么重要**: Agent 需要完成完整任务,而非单个 API 调用

**如何应用**:
- 合并相关操作(如 `schedule_event` 同时检查可用性和创建事件)
- 关注 Agent 实际需要完成的工作流
- 问:"用户想要完成什么?" 而非 "API 提供什么?"

**示例**:
```
❌ 错误:分离的工具
check_calendar_availability
create_calendar_event
send_event_notification

✅ 正确:单一工具
schedule_event(包含冲突检查和通知发送)
```

### 2.2 优化有限的上下文

**原则**: Agent 有受限的上下文窗口 - 让每个 token 都有价值

**为什么重要**: 当 Agent 上下文耗尽时,任务失败。冗长的输出迫使 Agent 做出困难决策

**如何应用**:
- 返回高价值信息,而非详尽的数据转储
- 提供"简洁" vs "详细"响应格式选项(默认简洁)
- 默认使用人类可读标识符而非技术代码(名称优于 ID)
- 实现字符限制和优雅截断(通常 25,000 字符)
- 使用合理的默认分页(20-50 项)

**示例**:
```
❌ 错误:返回用户对象的所有 50 个字段
✅ 正确:返回 name, email, role, key status 字段
         提供 detailed=true 参数获取完整数据
```

### 2.3 设计可操作的错误消息

**原则**: 错误消息应引导 Agent 正确使用,而非仅报告失败

**为什么重要**: Agent 通过反馈学习工具使用。清晰的教育性错误帮助 Agent 自我纠正

**如何应用**:
- 在错误消息中建议具体的下一步
- 使错误具有教育性,而非仅诊断性
- 参数无效时包含正确使用示例
- 引导 Agent 找到解决方案

**示例**:
```
❌ 错误:"Error 400: Invalid request"
✅ 正确:"limit 参数必须在 1-100 之间。你提供了 500。
         尝试使用 limit=50 并通过 offset 分页获取更多结果。"
```

### 2.4 遵循自然任务细分

**原则**: 工具名称和组织应反映人类思考任务的方式

**为什么重要**: Agent 使用工具名称和描述决定调用哪个工具。自然命名改善工具发现

**如何应用**:
- 工具名称应反映人类任务心智模型
- 使用一致的前缀分组相关工具
- 围绕自然工作流设计工具
- 使用面向动作的命名:search_users, create_project, send_message
- 包含服务/系统前缀避免冲突:slack_send_message

**示例**:
```
❌ 错误:api_endpoint_users_post, api_endpoint_users_get
✅ 正确:create_user, search_users, delete_user
```

### 2.5 使用评估驱动开发

**原则**: 早期创建现实评估场景,让 Agent 反馈驱动工具改进

**为什么重要**: 只有通过实际 Agent 测试才能发现可用性问题

**如何应用**:
- 创建 10+ 个复杂、现实的问题 Agent 应使用工具回答
- 用实际 AI Agent 测试解决这些问题
- 观察 Agent 在哪里挣扎、犯错或上下文耗尽
- 基于真实 Agent 表现迭代工具设计

## 三、上下文管理原则

### 3.1 简洁是关键(Concise is Key)

上下文窗口是公共资源。Skill 与其他所有内容共享上下文窗口:系统提示、对话历史、其他 Skill 元数据、实际用户请求。

**默认假设**: Agent 已经非常聪明。只添加 Agent 没有的上下文。

**挑战每条信息**:
- "Agent 真的需要这个解释吗?"
- "这段话是否值得它的 token 成本?"

**偏好**: 简洁示例胜过冗长解释

### 3.2 设置适当的自由度

匹配具体程度与任务的脆弱性和可变性:

| 自由度等级 | 适用场景 | 指导方式 | 示例 |
|-----------|---------|---------|------|
| **高** | 存在多种有效方法<br>模型的决策依赖上下文 | 提供启发式策略(给原则) | 代码审查:先看安全性,再看可读性 |
| **中** | 存在首选模式<br>允许一定程度的变通<br>行为受配置参数影响 | 提供模板/伪代码(给框架) | 报告生成:按"摘要-分析-建议"结构 |
| **低** | 操作脆弱且易错<br>一致性至关重要<br>必须遵循特定序列 | 提供可执行的脚本(给代码) | 数据库迁移:按固定顺序执行脚本 |

**比喻**: 将 Agent 视为探索路径——悬崖边的窄桥需要特定护栏(低自由度),而开阔田野允许多条路线(高自由度)

## 五、AI Agent 七大设计原则(优先级排序)

### P0 - 目标唯一性 & 任务边界清晰

**核心**: Agent 只解决**单一领域 / 一类目标**的问题,拒绝「万能 Agent」

```
❌ 错误示例
"办公全能 Agent" → 能力边界模糊,容易崩溃

✅ 正确示例
"文档总结 Agent" + "PPT生成 Agent" + "数据统计 Agent"
→ 每个 Agent 职责单一,可独立测试和迭代
```

**设计要求**:
- 明确 Agent 的**能力上限与下限**
- 清晰定义**需要人类介入的边界**
- 每个 Agent 任务控制在 **3-10 步**以内,确保模型不会"迷路"

### P1 - 最小自主性原则

**核心**: 自主性是一把双刃剑——自主性越强,智能度越高,但**可控性越差、出错概率越高、成本越高**

```
┌─────────────────────────────────────────────┐
│        自主性光谱                              │
│                                              │
│  低自主 ────────────────────────────── 高自主  │
│  │                                        │  │
│  确定性              模糊判断               │  │
│  低风险              高风险                 │  │
│  重复性              创造性                 │  │
│                                              │
│  ✅ Agent 应在此区间运作                     │
│  ❌ 付费/修改数据/高危指令必须人类决策       │
└─────────────────────────────────────────────┘
```

**设计要求**:
- 核心决策、高风险操作(付费调用、修改数据、执行高危指令)必须交给人类
- Agent 只做**「确定性的、低风险的、重复性的」**自主决策
- 不可逆操作必须使用确定性确认:"我将创建 X 包含 Y 字段 — 是否继续?"

### P2 - 可解释性 & 可追溯性

**核心**: Agent 的每一步决策、每一次工具调用,都要能给出**明确理由**

```
工具调用示例

❌ 无记录
调用了计算器

✅ 有记录
调用计算器 because: "需要计算复杂财务公式,自身算力不足"
```

**设计要求**:
- 所有行为**留痕**:任务拆解过程、工具调用记录、决策依据、执行结果
- 方便人类**复盘、调试、追责**
- 使用 OpenTelemetry 等工具实现可观测性

### P3 - 鲁棒性(容错性)

**核心**: Agent 必须能处理异常情况——工具调用失败、返回无效数据、用户输入模糊、任务目标无法达成

```
错误处理流程

工具调用失败
      │
      ▼
  重试 2次
      │
  ├─ 成功 → 继续执行
  │
  ▼
更换工具
      │
  ├─ 成功 → 继续执行
  │
  ▼
求助人类(人机协同)
```

**关键原则**:
- 出错**不崩溃**
- 能**重试 / 降级 / 终止 / 求助**
- **避免对 Agent 使用重试机制**:Agent 输出非确定性,重试不能保证改善
- 将错误信息显式写入上下文,让 LLM 学习错误模式并发起替代路径

### P4 - 效率优先,兼顾精准

**核心**: 复杂任务的规划与拆解**不要追求「最优解」,先追求「可行解」**

```
❌ 过度规划
任务拆解到极致细 → 计算成本高、执行耗时长

✅ 适度规划
拆解到「能执行、无歧义」即可
```

### P5 - 人机协同闭环

**核心**: 永远不要设计「完全自主的 Agent」,当前大模型推理能力**不足以支撑绝对可靠的自主决策**

```
核心规则
┌─────────────────┐
│  Agent 提方案   │  ← 模型擅长:分析、推理、生成选项
│    人类做决策    │  ← 人类擅长:判断价值、承担后果
├─────────────────┤
│  Agent 做执行   │  ← 模型擅长:重复性、确定性任务
│    人类做校验    │  ← 人类擅长:质量把控、异常识别
└─────────────────┘
```

**可控性实现**:
- 偏好设置:允许用户设置个人偏好(语言风格、详细程度等)
- 指令覆盖:用户指令应优先于 Agent 默认行为
- 中断机制:提供暂停、撤销、重置等控制选项

### P6 - 提示词即代码(Prompt as Code)

**核心**: 提示词是"具备版本控制的业务逻辑",不是临时文本

```
❌ 黑盒提示
使用 AutoPrompt 或链式提示框架
→ 优化难度大,不可追踪

✅ 自主提示
自己编写系统提示词,控制上下文和行为
→ 可调优、可测试、可部署
```

**黄金法则**:"提示词是会让你的 Agent 成败的关键因素" —— 投入 50%+ 开发时间在提示工程上

**最佳实践**:
- 为每个 Agent 配置独立提示词文件,版本化管理
- 使用结构化、多步推理:融入 Chain-of-Thought 风格
- 明确定义任务分解、推理方法和输出格式
- 描述**应该发生什么**而不是**不应该发生什么**
- 提供具体示例(few-shot)

## 六、设计原则检查清单

```markdown
□ 是否遵循单职责原则?
□ 触发条件是否明确?
□ 边界是否清晰?
□ 上下文是否优化?
□ 错误消息是否可操作?
□ 命名是否自然?
□ 是否有评估机制?
□ 安全性是否考虑?
□ 文档是否完善?
□ 是否持续迭代?
```
