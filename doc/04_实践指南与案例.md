## 一、Skill 开发流程

### 1.1 六步创建流程

```
理解 → 规划 → 初始化 → 编辑 → 校验 → 迭代
```

#### Step 1: 理解技能——用具体例子建立共识

> Skip this step only when the skill's usage patterns are already clearly understood.

要创建一个有效的 skill,必须先清楚理解**具体的使用例子**。这些理解可以来自用户提供的例子,也可以来自生成的、经用户验证的例子。

以构建 image-editor 技能为例,可以问用户:
- "image-editor 技能应该支持什么功能?编辑、旋转,还有其他吗?"
- "能给一些使用这个技能的例子吗?"
- "我能想到用户会说'去掉这张照片的红眼'或'旋转这张图片'。还有其他使用方式吗?"
- "用户会说什么话来触发这个技能?"

**注意**: 不要一次问太多问题。先问最重要的,然后根据需要跟进。

**完成标志**: 对技能应该支持的功能有了清晰的认识。

#### Step 2: 规划可复用的技能内容

对每个具体例子做两个分析:
1. 如果从零开始做这件事,需要什么?
2. 其中哪些会被反复使用?

反复使用的东西 → 封装成 scripts/references/assets

**案例 1: `pdf-editor` 技能**(用户问"帮我旋转这个 PDF")
- 旋转 PDF 每次都要重写同样的代码
- → 封装为 `scripts/rotate_pdf.py`

**案例 2: `frontend-webapp-builder` 技能**(用户问"帮我做一个 todo app"或"做一个步数追踪仪表盘")
- 写前端 webapp 每次都需要同样的 HTML/React 样板代码
- → 封装为 `assets/hello-world/` 模板目录

**案例 3: `big-query` 技能**(用户问"今天有多少用户登录了?")
- 查询 BigQuery 每次都要重新发现表的 schema 和关系
- → 封装为 `references/schema.md`

**完成标志**: 列出了所有要包含的可复用资源清单(scripts、references、assets)。

#### Step 3: 初始化技能

> When creating a new skill from scratch, always run the `init_skill.py` script.

这里用的是"always"——不是"建议",是"总是"。原因:
- 脚本生成的目录结构保证符合规范
- 模板中的 TODO 提醒确保不遗漏必需字段
- `agents/openai.yaml` 的格式约束(字段长度、引号规则)靠手写容易出错

这是**低自由度原则的直接应用**:初始化是一个脆弱操作,用脚本消除出错可能。

初始化后:
- 定制 SKILL.md 并根据需要添加资源
- 如果用了 `--examples`,替换或删除占位符文件

#### Step 4: 编辑技能

这是最核心的步骤,分两阶段:

**阶段一:先实现可复用资源**

从 Step 2 规划的资源开始:实现 `scripts/`、`references/`、`assets/` 文件。

注意:
- 这一步可能需要用户输入(比如 `brand-guidelines` 技能需要用户提供品牌素材)
- 新增的脚本**必须通过实际运行来测试**,确保无 bug 且输出符合预期
- 如果有很多类似的脚本,只需测试代表性样本来建立信心
- 如果用了 `--examples`,删除不需要的占位符文件。只创建真正需要的资源目录

**阶段二:更新 SKILL.md**

**Frontmatter 写法**:

```yaml
---
name: skill-name
description: >-
  描述技能做什么 + 具体什么时候用。
  把所有 "when to use" 信息放这里,不要放在 body 里。
---
```

**Body 写法**:

写给另一个 Codex 实例的操作指令。包含对 Codex 有帮助但不显而易见的信息:程序性知识、领域细节、可复用资源的使用方式。

统一使用**祈使语气/不定式**。

#### Step 5: 校验技能

```bash
scripts/quick_validate.py <path/to/skill-folder>
```

校验 YAML frontmatter 格式、必需字段、命名规则。不通过就修复后重新运行。

#### Step 6: 迭代

> After testing the skill, users may request improvements. Often this happens right after using the skill, with fresh context of how the skill performed.

迭代工作流:
1. 在真实任务上使用技能
2. 发现吃力或低效的地方
3. 找出 SKILL.md 或捆绑资源该如何更新
4. 实施变更并重新测试

好的 skill 不是一次写成的。skill-creator 创建的 laotou-thought-style 技能,在第一次生成后就迭代了 `openai.yaml` 的 `short_description` 和 `default_prompt`——从泛泛的描述变为更精确的操作指令。

## 二、核心最佳实践

### 2.1 清晰的判断条件和错误处理

在 Skill 中要写清楚:
- 需不需要先检查?
- 如果失败了该提示什么?
- 怎么返回上一步?

**示例**:
```markdown
## 错误处理
如果遇到以下情况:
1. 文件不存在 → 提示用户并提供文件路径建议
2. 格式不支持 → 列出支持的格式并询问是否转换
3. 权限不足 → 提供权限获取指南
```

### 2.2 保持 SKILL.md 简洁

- 建议控制在 500 行左右
- 多了就拆文件,但避免多层嵌套引用
- 使用 Bundled Resources 存储大量内容

**资源组织**:
- `scripts/`: 重复写的代码、需要确定性执行的逻辑
- `references/`: 大块文档、API、schema、长规范
- `assets/`: 模板、pptx、html boilerplate、字体等

### 2.3 使用祈使语气

在指令中使用祈使形式:

**✅ 好的写法**:
```markdown
## 执行步骤
1. 读取配置文件
2. 验证参数
3. 执行迁移
```

**❌ 坏的写法**:
```markdown
## 执行步骤
你应该先读取配置文件,然后验证参数,最后执行迁移
```

### 2.4 解释"为什么"而非强制"必须"

尝试解释为什么事情很重要,而不是使用沉重的 MUST。

**✅ 好的写法**:
```markdown
## 安全检查
在处理用户输入前进行验证很重要,因为这可以防止:
- SQL 注入攻击
- XSS 跨站脚本攻击
- 数据泄露风险
```

**❌ 坏的写法**:
```markdown
## 安全检查
MUST 验证所有用户输入
MUST 使用参数化查询
MUST 转义特殊字符
```

### 2.5 写约束时,"不做什么"比"做什么"更精确

简洁不只是"少写",还包括"写对"。看一个例子。

当 skill-creator 创建 `laotou-thought-style`(一种写作风格技能)时,它**没有**写:

```
请用温暖、克制、有洞察力的语气写作。
```

这种正面描述看起来清晰,但对 AI 来说,"温暖"的程度、"克制"和"有洞察力"之间的平衡——全是模糊空间。

它做的是写了一份**反模式清单**(`references/anti-patterns.md`):

| 不要这样做 | 症状 | 怎么改 |
|-----------|------|--------|
| 角色堆砌 | 连续出现多个名字和对白 | 保留一个冲突场景,补抽象提炼 |
| 只有鸡汤没有动作 | 全文"要坚持、要努力" | 改为今天可做的一小步 |
| 直接大道理 | 开头就讲规律 | 先铺生活场景 |
| 收尾太猛 | 结尾"必须改变!" | 换成"慢慢来""就好" |
| 过度绝对化 | "永远""一定" | 加限定词"多数时候""往往" |

**每一条都是具体的、可检测的、有明确修正方案的。**

背后的原理:

```
"做什么" → 描述一个无限大的可行域 → AI 在里面随机游走
"不做什么" → 在可行域上画边界 → AI 的行为空间被收窄到你想要的范围
```

## 三、优秀 Skill 案例分析

### 3.1 Self-Improving Agent(自我改进代理)

**最创新的 Skill 之一**

- **自我反思** — 评估自身工作,发现错误
- **自我批评** — 识别改进机会
- **自我学习** — 永久改进
- **自我组织记忆** — 自动记忆整理

```
核心能力:
- 自动记忆整理(Auto-memory curation)
- 模式提升(Pattern promotion)
- Skill 提取(Skill extraction)
- 记忆健康检查(Memory health)
```

### 3.2 RAG Architect(RAG 架构师)

**企业级 RAG 系统构建**

- RAG 管道构建器
- 分块优化器
- 检索评估器

### 3.3 Skill Security Auditor(Skill 安全审计员)

**安全第一的设计理念**

扫描内容:
- 命令注入
- 代码执行
- 数据泄露
- 提示注入
- 依赖供应链风险
- 权限提升

### 3.4 Agent Designer(代理设计器)

**多代理编排核心**

- 多代理编排
- 工具模式
- 性能评估

### 3.5 OWASP Security Skill

**Web 安全标准**

- OWASP Top 10:2025
- ASVS 5.0
- Agentic AI Security (2026)
- 支持 20+ 编程语言的代码审查检查清单

## 四、常见错误与避坑指南

### 4.1 十大常见错误

#### 1. 违反单职责原则

```
❌ 一个 Skill 做所有事
✅ 拆分为多个专业 Skill
```

#### 2. 边界模糊

```
❌ 触发条件不明确
✅ 清晰定义何时调用、何时不调用
```

#### 3. 忽略上下文限制

```
❌ 返回大量冗余数据
✅ 优化 token 使用,提供简洁输出
```

#### 4. 错误消息不友好

```
❌ "Error 400: Invalid request"
✅ "limit 参数必须在 1-100 之间。你提供了 500。
    尝试使用 limit=50 并通过 offset 分页。"
```

#### 5. 命名不规范

```
❌ api_endpoint_users_post
✅ create_user
```

#### 6. 缺少评估

```
❌ 凭感觉判断效果
✅ 建立量化指标,A/B 测试验证
```

#### 7. 过度设计

```
❌ 添加不必要的复杂性
✅ 保持简单,按需扩展
```

#### 8. 忽视安全性

```
❌ 直接执行用户输入
✅ 验证输入,隔离指令,过滤输出
```

#### 9. 文档缺失

```
❌ Skill 散落各处,无版本管理
✅ 建立 Skill 库,版本控制,文档化
```

#### 10. 忽略迭代

```
❌ 一次设计期望完美
✅ 持续优化,永不满足
```

### 4.2 常见反模式

#### 反模式 1: 过度约束

❌ **问题**: 使用过多的 MUST/ALWAYS/NEVER
✅ **解决**: 解释原因和背景,让模型理解意图

#### 反模式 2: 过于抽象

❌ **问题**: 缺乏具体示例和操作指南
✅ **解决**: 提供清晰的输入输出示例

#### 反模式 3: 忽视上下文限制

❌ **问题**: SKILL.md 过长,占用过多上下文
✅ **解决**: 使用渐进式披露,拆分到 references/

#### 反模式 4: 触发条件不明确

❌ **问题**: description 缺乏具体的触发时机
✅ **解决**: 明确说明"何时使用",包含关键词和场景

## 五、评估与优化

### 5.1 评估指标体系

#### 质量维度

| 维度 | 指标 | 测量方法 |
|------|------|----------|
| 准确性 | 正确率、F1 分数 | 人工标注 + 自动评估 |
| 相关性 | 上下文相关性评分 | RAG Triad 评估 |
| 完整性 | 信息覆盖率 | 需求检查清单 |
| 一致性 | 多次输出相似度 | Self-Consistency |
| 可读性 | Flesch 阅读分数 | 自动化工具 |

#### 性能维度

| 维度 | 指标 | 目标值 |
|------|------|--------|
| 响应时间 | 平均延迟 | < 2s |
| Token 消耗 | 输入/输出 Token 数 | 最小化 |
| 成本效益 | 单次调用成本 | < $0.01 |
| 稳定性 | 成功率 | > 99% |
| 上下文效率 | Token/信息比 | 优化 |

### 5.2 A/B 测试方法

```markdown
测试设计:
- 对照组(A):原始 Skill
- 实验组(B):优化后 Skill
- 样本量:每组至少 100 个测试用例
- 评估维度:准确性、相关性、用户满意度

统计检验:
- 显著性水平:p < 0.05
- 效应量:Cohen's d > 0.5
```

### 5.3 迭代优化循环

```
1. 基线测试 → 建立性能基准
     ↓
2. 问题诊断 → 识别薄弱环节
     ↓
3. 方案设计 → 制定优化策略
     ↓
4. 实施改进 → 修改 Skill
     ↓
5. 效果验证 → 对比测试结果
     ↓
6. 文档更新 → 记录优化历史
     ↓
[循环迭代]
```

### 5.4 验证策略

| 策略 | 示例 |
|------|------|
| 运行代码 | "构建解析器,在 test-input.json 上运行并验证输出" |
| 视觉比较 | "实现设计[截图],截图结果并比较差异" |
| 测试套件 | "先写测试,然后实现直到所有测试通过" |
| Lint 检查 | "每次更改后运行 npm run lint 和 typecheck" |
| 端到端检查 | "启动服务器,curl /health 端点,验证返回 200" |
| 标准文件 | "每次迭代后读取 CRITERIA.md 并检查完成项" |

## 七、优秀 Skill 的核心特征

1. **清晰的触发条件** — Description 精确描述何时使用
2. **结构化工作流** — 步骤明确,可重复执行
3. **自我验证能力** — 包含测试和验证机制
4. **模块化设计** — 可组合、可扩展
5. **安全意识** — 权限控制、工具限制
6. **持续改进** — 支持迭代优化
