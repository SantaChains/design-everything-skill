## 一、谷歌 5 种 Skill 设计模式

谷歌 Cloud Tech 提出的 5 种 Skill 设计模式,旨在解决 Agent 开发中"格式规范统一但执行效果差异大"的核心痛点。

### 模式 1: Tool Wrapper(工具包装器)

**内核**: 将外部库或团队规范封装为动态加载的 Skill,按需调用

**优势**: 保持系统提示词精简,避免硬编码,实现规范的"即插即用"

**典型场景**: FastAPI 开发规范、内部编码标准分发

### 模式 2: Generator(生成器)

**内核**: 分离"结构"与"内容",通过模板(`assets/`)和风格指南(`references/`)驱动标准化输出

**优势**: 解决输出结构混乱问题,通过更换模板实现多场景复用(如技术报告、API 文档)

**典型场景**: 自动化生成结构化文档、代码片段

### 模式 3: Reviewer(审查器)

**内核**: 模块化检查清单,将审查规则外置到参考文档,动态加载

**优势**: 避免提示词冗长,通过更换检查清单快速切换审查维度(如代码质量→安全审计)

**典型场景**: Python 代码审查、OWASP 安全审计

### 模式 4: Inversion(反转模式)

**内核**: 将"用户驱动 Agent"反转为"Agent 面试用户",通过分阶段提问强制需求澄清

**优势**: 对抗 Agent"盲目猜测"本能,确保复杂需求理解准确

**典型场景**: 项目规划、需求调研(需多轮交互的场景)

### 模式 5: Pipeline(流水线模式)

**内核**: 用"硬检查点"确保多步骤流程严格有序,禁止跳步

**优势**: 解决任务中断或遗漏问题,通过门禁指令(如`Do NOT proceed until user confirms`)保证质量

**典型场景**: API 文档生成、多阶段代码重构

### 模式选择决策树

| **需求场景**               | **推荐模式**         |
|---------------------------|---------------------|
| 让 Agent 掌握特定库/规范     | Tool Wrapper        |
| 输出固定格式内容           | Generator           |
| 检查/评审代码或文档        | Reviewer            |
| 需求复杂易误解             | Inversion           |
| 多步骤任务不可跳步         | Pipeline            |

### 高阶技巧与组合策略

- **模式组合**: Pipeline 可嵌入 Reviewer 实现自检,Generator 可结合 Inversion 先收集信息再填充模板
- **渐进式加载**: 利用 ADK 的 SkillToolset 机制,按需加载 Skill,避免 Token 爆炸
- **设计本质**: 所有模式均通过"约束 Agent 本能"(如跳步、猜测)提升可靠性,核心是**将业务逻辑抽象为可复用的流程**

## 二、经典设计框架

### 2.1 RTF 框架(Role-Task-Format)

经过上万次实验验证,最高效的 Skill 结构:

#### 1. Role(角色设定)

**作用**: 激活模型专业能力

**错误示例**:
```
"帮我写文案"
```

**正确示例**:
```
"你是拥有 5 年经验的小红书美妆博主"
```

#### 2. Task(任务描述)

**作用**: 使用行为动词明确目标

**错误示例**:
```
"写产品介绍"
```

**正确示例**:
```
"撰写一款敏感肌适用的防晒霜推广文案"
```

#### 3. Format(格式约束)

**作用**: 规定输出结构与风格

**错误示例**:
```
"要吸引人"
```

**正确示例**:
```
"使用 emoji 分隔卖点,每段不超过 30 字,
结尾添加 #敏感肌防晒 话题标签"
```

### 2.2 RACE 框架

OpenAI 官方指南推荐的设计模型:

#### R - Role(角色)

定义 AI 的身份和专业领域

```
你是《自然》杂志的环境专栏作家
```

#### A - Action(行动)

明确要执行的具体动作

```
请写一篇 800 字的深度报道
```

#### C - Context(情境)

提供背景信息和约束条件

```
分析微塑料污染对海洋生态的影响,
需引用 2024 年联合国环境署报告数据
```

#### E - Expectation(期望)

定义成功标准和输出格式

```
采用'问题-原因-解决方案'结构,
语言风格兼顾科学性与可读性
```

### 2.3 Five C's Framework

#### 1. Clarity(清晰性)

**为什么重要**: 消除歧义;定义角色、语气、受众

**快速胜利**:
```
"You are an AP Pre-Calculus tutor …"
```

#### 2. Context(上下文)

**为什么重要**: 提供相关背景事实

**快速胜利**:
```
嵌入简短摘录或向量检索
```

#### 3. Constraints(约束)

**为什么重要**: 规定格式、长度、禁止短语

**快速胜利**:
```
"Return JSON with keys …"
```

#### 4. Creativity(创造性)

**为什么重要**: 控制温度、角色提示

**快速胜利**:
```
"Add one witty analogy; temperature 0.7"
```

#### 5. Continuous iteration(持续迭代)

**为什么重要**: A/B 测试和优化

**快速胜利**:
```
使用 LangSmith Hub 等 Prompt IDE
```

## 三、吴恩达四大设计范式

2024-2025 年吴恩达提出,已被 Google、OpenAI 等企业广泛应用:

### 范式一: 反思(Reflection)

Agent 能够**自我审视**输出,发现错误后自我修正

```
输出内容
    │
    ▼
自我检查(LLM评估)
    │
  ├─ 合格 → 输出
  │
  └─ 不合格 → 修正 → 重新检查
```

**实现方式**:
- **单 Agent 自反思**: 生成后自我评估
- **双 Agent 协作**: Generator + Critic(通常效果更好)

**适用场景**: 写作与内容创作、代码生成、分析与推理任务

**关键问题**:
- 我学到了什么?
- 这是否有助于达成目标?
- 置信度如何?
- 下一步应该继续还是改变策略?

### 范式二: 工具调用(Tool Use)

Agent 能调用外部工具扩展能力边界

```
工具类型          示例格式
─────────────────────────────────────
API类           { "action": "call_api", "endpoint": "weather" }
计算类           { "action": "calculate", "expression": "5 + 3" }
控制类           { "action": "request_human_input" }
```

**工具设计原则**:
- 工具即"可执行结构化输出"
- 每个工具本质是一种 JSON 格式的命令
- 工具名称使用小写字母数字,无空格或特殊字符
- 文档化工具 thoroughly(ACI 与提示词同等重要)
- 包含示例和边界情况
- 使用结构化输出(JSON Schema)确保可靠性

### 范式三: 规划(Planning)

Agent 能将复杂任务**分解为可执行的子步骤**

```
复杂任务
    │
    ▼
任务拆解
    │
    ▼
子任务1 → 子任务2 → 子任务3
    │         │         │
    ▼         ▼         ▼
  执行     执行      执行
    │         │         │
    └─────────┴─────────┘
              │
              ▼
         结果聚合 + 校验
```

**规划变体**:
- **静态规划**: 一次性规划,按序执行
- **动态规划**: 根据结果重新规划
- **层次化规划**: 计划中嵌套子计划

**ReAct 框架**: Reasoning(推理) + Acting(行动) + Observation(观察)循环

### 范式四: 多 Agent 协同(Multi-Agent Collaboration)

多个专业 Agent **分工协作**,各自负责单一领域

```
┌──────────────────────────────────────────────┐
│               多 Agent 协作模式                  │
│                                               │
│    analyst ──→ architect ──→ implementer     │
│      │              │              │           │
│      ↓              ↓              ↓          │
│   分析需求        设计方案        代码实现      │
│      │              │              │           │
│      └──────────────┴──────────────┘           │
│                       │                        │
│                       ▼                        │
│                    qa(质量检查)                │
│                       │                        │
│                       ▼                        │
│                 反馈 → analyst(复盘)          │
└──────────────────────────────────────────────┘
```

**协作模式**:
- **流水线模式**: 顺序执行,各 Agent 处理特定阶段
- **路由模式**: 根据输入分类,分发给不同 Agent
- **编排者-工作者**: 中央编排器动态分配任务给工作者 Agent
- **辩论模式**: 多个 Agent 讨论达成共识

## 四、Anthropic 六大工作流模式

根据 Anthropic 2025 年研究,以下工作流模式按复杂度递增:

### 4.1 Prompt Chaining(提示链)

将任务分解为固定顺序的子任务,每个 LLM 调用处理前一个调用的输出

**适用**: 任务可清晰分解为固定子任务,且每个步骤输出可预测

### 4.2 Routing(路由)

对输入分类,路由到专用任务或模型处理

**适用**: 存在不同类别的复杂任务,且类别可预先定义

### 4.3 Parallelization(并行化)

将任务分解为可并行执行的独立子任务

**两种形式**:
- **分段**: 将任务拆分为独立子任务并行处理
- **投票**: 多次运行相同任务获得多样化结果

**适用**: 子任务可并行化且速度比准确性更重要

### 4.4 Orchestrator-Workers(编排者-工作者)

中央编排器动态分解任务,分配给工作者 Agent,并综合结果

**适用**: 复杂任务需要动态、自适应的子任务分解

### 4.5 Evaluator-Optimizer(评估者-优化者)

一个 Agent 生成输出,另一个 Agent 评估并提供改进反馈

**适用**: 有明确评估标准且迭代优化能提供可衡量价值

### 4.6 Autonomous Agent(自主 Agent)

Agent 自主规划、执行、反思,无需人工干预

**适用**: 开放式问题,步骤数量无法预测,无法硬编码固定路径

## 五、高级技术方法

### 5.1 Chain-of-Thought (CoT) 思维链

**核心原理**: 引导模型展示推理过程,而非直接给出答案

**性能提升**: 数学推理准确率从 17.7% 提升至 78.7%(Kojima et al., 2022)

#### Zero-shot CoT

```
问题:一个篮子里有 23 个苹果,拿走 5 个,又放进 8 个,现在有多少个?

❌ 无 CoT:
答案:26 个

✅ Zero-shot CoT:
Let's think step by step:
1. 初始篮子里有 23 个苹果
2. 拿走 5 个:23 - 5 = 18 个
3. 放进 8 个:18 + 8 = 26 个
答案:26 个
```

#### Few-shot CoT

```markdown
问题:小明有 15 元,买了 3 支铅笔,每支 2 元,还剩多少钱?

示例推理过程:
1. 计算铅笔总花费:3 支 × 2 元/支 = 6 元
2. 计算剩余金额:15 元 - 6 元 = 9 元
答案:9 元

现在请解决:
问题:书店有 120 本书,卖出 45 本,又进货 30 本,现在有多少本?
```

### 5.2 Tree-of-Thought (ToT) 思维树

**适用场景**: 需要探索多个解决方案的复杂问题

**核心机制**:
1. 生成多个候选思路
2. 评估每个思路的可行性
3. 选择最优路径或综合多个路径

**实战案例**:

```markdown
任务:设计一个高并发电商系统的架构方案

请按以下步骤思考:

步骤1:生成 3 个不同的架构思路
- 思路A:[描述]
- 思路B:[描述]
- 思路C:[描述]

步骤2:评估每个思路
- 思路A 优势:... 劣势:... 适用场景:...
- 思路B 优势:... 劣势:... 适用场景:...
- 思路C 优势:... 劣势:... 适用场景:...

步骤3:选择最优方案并说明理由
推荐方案:思路X
理由:...
```

### 5.3 Graph-of-Thought (GoT) 思维图

**适用场景**: 需要综合多个信息源的复杂推理

**核心特征**:
- 将推理过程建模为图结构
- 支持非线性、多路径推理
- 可回溯和修正推理路径

### 5.4 Self-Consistency 自一致性

**技术原理**: 生成多个推理路径,通过投票选择最一致答案

**性能提升**: 在 CoT 基础上再提升 12-18%

**实施步骤**:
1. 使用相同提示生成 5-10 个不同推理路径
2. 提取每个路径的最终答案
3. 统计答案出现频率
4. 选择频率最高的答案

### 5.5 Automatic Prompt Engineering (APE)

**核心思想**: 让 LLM 自己生成和优化 Prompt

**实施流程**:
```
人类意图 → LLM 生成候选 Prompt → 测试评估 → 迭代优化 → 最优 Prompt
```

**实战示例**:

```markdown
任务:生成一个用于代码审查的 Prompt

请生成 3 个不同的代码审查 Prompt 版本,每个版本关注不同方面:
- 版本1:关注安全性
- 版本2:关注性能优化
- 版本3:关注代码质量

然后评估每个版本,选择最优方案。
```

## 六、Skill 编排协议

| 模式 | 描述 | 适用场景 |
|------|------|----------|
| Solo Sprint | 跨项目阶段切换 Persona | 个人项目、MVP |
| Domain Deep-Dive | 一个 Persona + 多个堆叠 Skills | 架构审查、合规审计 |
| Multi-Agent Handoff | Persona 互相审查输出 | 高风险决策、发布准备 |
| Skill Chain | 顺序 Skills,无需 Persona | 内容管道、可重复检查清单 |

## 七、核心结论

- **格式已死,设计永生**: SKILL.md 的 YAML 格式已标准化,竞争力在于设计模式的灵活运用
- **约束即价值**: Agent 天生倾向于简化流程,而优秀 Skill 需通过结构强制其遵循规范
- **生产级实践**: 复杂场景需组合模式(如 Pipeline+Reviewer+Tool Wrapper),形成可编排的 Atomic Skill 架构
