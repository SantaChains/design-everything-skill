> 本文档包含 AI Agent 设计与 Prompt Engineering 的完整理论体系与实践方法。

## AI Agent 设计核心

### AI Agent 核心定义

AI Agent 是具备**「感知 → 思考 → 决策 → 执行 → 反馈 → 迭代」**闭环能力的自主智能系统。

| 对比维度 | ChatBot | Copilot | AI Agent |
|----------|---------|---------|----------|
| LLM依赖 | ✅ 基础交互 | ✅ 任务辅助 | ✅ 核心引擎 |
| 自主决策 | ❌ 预设规则 | ❌ 固定流程 | ✅ 动态调整 |
| 自动执行 | ❌ 仅文本输出 | ✅ 固定流程 | ✅ 自主工具调用 |

### Workflows vs Agents

| 类型 | 定义 | 控制方 | 适用场景 |
|------|------|--------|----------|
| **Workflows** | LLM 通过预定义代码路径编排 | 开发者控制流程 | 步骤可预测、确定性任务 |
| **Agents** | LLM 动态指导自身流程和工具使用 | LLM 控制流程 | 步骤不可预测、开放式任务 |

**黄金法则**：从最简单方案开始，仅在必要时增加复杂度。

---

### 七大设计原则

| 优先级 | 原则 | 核心要点 |
|--------|------|----------|
| **P0** | 目标唯一性 | Agent 只解决单一领域问题，拒绝「万能 Agent」 |
| **P1** | 最小自主性 | 高风险操作必须人类决策，Agent 只做确定性低风险决策 |
| **P2** | 可解释性 | 每一步决策都要能给出明确理由 |
| **P3** | 鲁棒性 | 出错不崩溃，能重试/降级/终止/求助 |
| **P4** | 效率优先 | 不追求最优解，先追求可行解 |
| **P5** | 人机协同 | Agent 提方案，人类做决策；Agent 做执行，人类做校验 |
| **P6** | 提示词即代码 | 投入 50%+ 开发时间在提示工程上 |

按复杂度递增：

| 模式 | 描述 | 适用场景 |

### 谷歌 5 种 Skill 设计模式

| 模式 | 内核 | 适用场景 |
|------|------|----------|
| **Tool Wrapper** | 将外部库/规范封装为动态加载的 Skill | 让 Agent 掌握特定库/规范 |
| **Generator** | 分离"结构"与"内容"，模板驱动输出 | 输出固定格式内容 |
| **Reviewer** | 模块化检查清单，审查规则外置 | 检查/评审代码或文档 |
| **Inversion** | Agent 面试用户，分阶段提问澄清需求 | 需求复杂易误解 |
| **Pipeline** | 硬检查点确保多步骤流程严格有序 | 多步骤任务不可跳步 |

**模式选择决策树**：
- 让 Agent 掌握特定库/规范 → Tool Wrapper
- 输出固定格式内容 → Generator
- 检查/评审代码或文档 → Reviewer
- 需求复杂易误解 → Inversion
- 多步骤任务不可跳步 → Pipeline

### Self-Improving Agent 自我改进机制

**核心理念**："Correct once, never again"——用户纠正一次，Agent 永远记住。

**三层置信度机制**：

| 级别 | 信号 | 处理 |
|------|------|------|
| 🔴 HIGH | 显式纠正（"不用 X，用 Y 代替"） | 创建 Critical Corrections |
| 🟡 MEDIUM | 批准（"很好，就是这样"） | 添加到 Best Practices |
| 🟢 LOW | 观察（"你有没有考虑..."） | 记录到 Considerations |

**自研发生习循环**：
```
用户纠正 → 信号检测 → 模式匹配 → Skill 更新 → 永久记忆
    ↑                                              ↓
    └────────────── 下次自动应用 ←──────────────────┘
```

### Agent 反模式清单

```
❌ 万能Agent        一个Agent处理所有任务 → 能力边界模糊
❌ 纯自主Agent      无人类介入点 → 错误无法纠正
❌ 黑盒Prompt      不可追踪/测试 → 难以调试
❌ 硬编码控制流     缺乏灵活性 → 无法应对异常
❌ 缺乏错误处理     工具失败即崩溃 → 系统不稳定
❌ 无状态设计       每次调用丢失上下文 → 无法连续推理
❌ 过度工程化       为简单任务构建复杂系统 → 得不偿失
❌ 糟糕提示词       模糊指令、缺少示例 → 性能差
❌ 单一共享记忆     所有Agent共用记忆 → 混乱和冲突
❌ 隐藏错误         错误不暴露 → 无法调试和改进
❌ 缺少评估         无评估标准 → 无法衡量和改进
```

### Skill 开发最佳实践

**评测驱动开发流程**：
1. **建立基线**：先让模型直接执行任务，记录失败场景
2. **定义评测用例**：优先编写 3-5 个具体用例，明确通过/失败标准
3. **编写最小化 Skill**：只实现通过评测的最短路径
4. **补充边界与示例**：扩展时需新增评测支撑
5. **评测回归与迭代**：每次修改后必须回归测试
6. **真实场景校准**：结合使用反馈形成闭环迭代

**高命中率 Skill 设计标准**：
- 精准的元数据（name + description 简洁明确）
- 自由度分级（根据任务复杂度控制约束强度）
- 职责单一、边界清晰、最小必要信息

## Prompt Engineering 核心

### Skill vs Prompt vs MCP 边界

| 类型 | 本质 | 特点 |
|------|------|------|
| **Prompt** | 一次性对话指令 | 每次重新描述，手动复制粘贴 |
| **Skill** | 能力封装模块 | 可复用、渐进式加载、自动触发 |
| **MCP** | 能力扩展接口 | 连接 API、数据库、外部工具 |

**Skill 核心价值**：把"某类事情应该怎么专业做"封装成可复用、可自动触发的能力模块。

---

### 三级渐进式加载系统

| 层级 | 内容 | 何时加载 | Token 成本 |
|------|------|----------|-----------|
| **L1** | Frontmatter（name + description） | 始终常驻 | ~100 词 |
| **L2** | SKILL.md Body | Skill 触发时 | <5k 词 |
| **L3** | Bundled Resources（scripts/references/assets） | 按需加载 | 无上限 |
| **L4** | Scripts 执行 | **零 Token** | 0 |

**L4 Scripts 特性**：脚本执行不占用上下文窗口，实现零 token 开销。

### RTF 框架（Role-Task-Format）

经过上万次实验验证，最高效的 Prompt 结构：

```
┌─────────────────────────────────────────────┐
│                  RTF 框架                    │
├─────────────────────────────────────────────┤
│  Role（角色设定）→ 激活模型专业能力          │
│  Task（任务描述）→ 使用行为动词明确目标       │
│  Format（格式约束）→ 规定输出结构与风格       │
└─────────────────────────────────────────────┘
```

**示例**：
```
❌ 错误："帮我写文案"
✅ 正确：
Role: "你是拥有 5 年经验的小红书美妆博主"
Task: "撰写一款敏感肌适用的防晒霜推广文案"
Format: "使用 emoji 分隔卖点，每段不超过 30 字，结尾添加 #敏感肌防晒 话题标签"
```

### RACE 框架

OpenAI 官方指南推荐的设计模型：

| 组件 | 含义 | 示例 |
|------|------|------|
| **R** | Role（角色） | 你是《自然》杂志的环境专栏作家 |

| **C** | Context（情境） | 分析微塑料污染对海洋生态的影响 |
| **E** | Expectation（期望） | 采用"问题-原因-解决方案"结构 |

### Five C's Framework

| 组件 | 重要性 | 快速胜利 |
|------|--------|----------|
| **Clarity**（清晰性） | 消除歧义，定义角色、语气、受众 | "You are an AP Pre-Calculus tutor…" |
| **Context**（上下文） | 提供相关背景事实 | 嵌入简短摘录或向量检索 |
| **Constraints**（约束） | 规定格式、长度、禁止短语 | "Return JSON with keys…" |
| **Creativity**（创造性） | 控制温度、角色提示 | "Add one witty analogy; temperature 0.7" |
| **Continuous iteration**（持续迭代） | A/B 测试和优化 | 使用 LangSmith Hub 等 Prompt IDE |

### 自由度分级光谱

```
┌─────────────────────────────────────────────────────────────┐
│                    自由度光谱                                │
│                                                             │
│  高自由度 ←─────────────────────────────────────→ 低自由度   │
│  │                                                    │     │
│  文字引导          伪代码/参数脚本           具体脚本    │
│  │                                                    │     │
│  多种方法有效      有最佳实践可变通         操作脆弱易错 │
│  决策依赖上下文    配置影响行为             一致性关键   │
│  启发式指导        模板+约束               必须遵循序列  │
│                                                             │
│  示例：创意写作     示例：报告生成          示例：数据库迁移 │
└─────────────────────────────────────────────────────────────┘
```

**判断标准**：
- 做错了后果多严重？ → 越严重 → 越低自由度
- 有多少种"正确"的做法？ → 越多 → 越高自由度

### SKILL.md 写作规范

#### Frontmatter 规范

```yaml
---
name: skill-name                    # 必填：hyphen-case，≤64字符
description: |                      # 必填：≤1024字符
  描述功能 + 触发时机。
  把所有"when to use"信息放这里，不要放在 body 里。
---
```

**关键规则**：
- description 是触发机制的**唯一来源**
- 不要在 frontmatter 中放 `name` 和 `description` 以外的字段

#### Body 写作规范

**统一使用祈使语气**：
```
✅ 正确：1. 读取配置文件  2. 验证参数  3. 执行迁移
❌ 错误：你应该先读取配置文件，然后验证参数...
```

**解释"为什么"而非强制"必须"**：
```
✅ 正确：在处理用户输入前进行验证很重要，因为这可以防止 SQL 注入攻击
❌ 错误：MUST 验证所有用户输入
```

### 四种经典骨架模式

| 模式 | 结构 | 适用场景 |
|------|------|----------|
| **Workflow-based**（流程型） | Overview → Workflow → Step 1 → Step 2… | 有固定顺序的任务 |
| **Task-based**（任务菜单型） | Overview → Quick start → Task 1 → Task 2… | 同一领域多种操作 |
| **Reference/Guidelines**（规范型） | Overview → Guidelines → Specifications | 固化品牌规范、代码风格 |
| **Capabilities-based**（能力清单型） | Overview → Core capabilities → 1,2,3… | 综合性系统能力 |

### 高级写作技巧

#### 技巧一：提高天花板 - 从"做任务"到"创流派"

```
❌ 普通："帮我用 p5.js 画图"
✅ 高级："创立一个美学流派 + 对应的算法体系"
```

#### 技巧二：双阶段结构 - 哲学 → 实现

强制抽象层在前，避免模型直接掉进"写代码、调数值"的局部最优。

#### 技巧三：写"不做什么"比"做什么"更精确

```
"做什么" → 描述一个无限大的可行域 → AI 在里面随机游走
"不做什么" → 在可行域上画边界 → AI 的行为空间被收窄
```

### Bundled Resources 四种类型

| 类型 | 用途 | 示例 |
|------|------|------|
| **scripts/** | 确定性/重复性任务的可执行代码 | `rotate_pdf.py`、`validate.py` |
| **references/** | 按需加载到上下文的文档 | `schema.md`、`api_docs.md` |
| **assets/** | 输出中使用的文件（模板、图标） | `logo.png`、`template.pptx` |
| **agents/openai.yaml** | 面向 UI 的元数据 | `display_name`、`short_description` |

**关键区别**：
- scripts 是给 AI **执行**的
- references 是给 AI **读**的
- assets 是**直接用在产出里**的

### 六步创建流程

```
Step 1: 理解技能 → 用具体例子建立共识
    ↓
Step 2: 规划内容 → 分析哪些会被反复使用
    ↓
Step 3: 初始化 → 运行 init_skill.py 脚本
    ↓
Step 4: 编辑技能 → 先实现资源，再更新 SKILL.md
    ↓
Step 5: 校验技能 → 运行 quick_validate.py
    ↓
Step 6: 迭代优化 → 真实任务测试 → 反馈改进
```

### 常见反模式清单

```
❌ 触发条件放在 body 里         → body 是触发后才加载的，晚了
❌ "When to Use" 写在 body      → 移到 description
❌ 参考细节塞进 SKILL.md        → 拆到 references/
❌ 确定性操作写成文字指令       → 封装成 scripts/
❌ references 互相引用          → 所有 references 从 SKILL.md 直接链接
❌ SKILL.md 和 references 内容重复 → 信息只在一处存在
❌ 给脆弱任务太多自由度         → 用脚本锁死格式
❌ 给创造性任务太多约束         → 给方向，不锁定具体用词
```

### Agent-Centric 设计五原则

| 原则 | 核心要点 |
|------|----------|
| **为工作流设计** | 设计高影响力工作流工具，而非简单包装 API |
| **优化有限上下文** | 返回高价值信息，默认简洁，实现字符限制 |
| **可操作的错误消息** | 错误消息应引导正确使用，包含下一步建议 |
| **自然任务细分** | 工具名称应反映人类任务心智模型 |
| **评估驱动开发** | 创建 10+ 现实评估场景，用 Agent 反馈驱动改进 |

---

### 评估驱动开发流程

```
1. 创建 10+ 复杂、现实的评估问题
     ↓
2. 用实际 AI Agent 测试
     ↓
3. 观察挣扎点、错误、上下文耗尽
     ↓
4. 基于真实表现迭代 Skill 设计
     ↓
5. 重复直到满意
```
