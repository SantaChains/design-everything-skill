## 一、AI Agent 核心定义

AI Agent（智能体）是具备**「感知 → 思考 → 决策 → 执行 → 反馈 → 迭代」**闭环能力的自主智能系统，核心是**「以目标为核心，自主完成复杂任务」**。

### 1.1 与传统应用的核心差异

| 对比维度 | ChatBot | Copilot | AI Agent |
|----------|---------|---------|----------|
| LLM依赖 | ✅ 基础交互 | ✅ 任务辅助 | ✅ 核心引擎 |
| 自主决策 | ❌ 预设规则 | ❌ 固定流程 | ✅ 动态调整 |
| 自动执行 | ❌ 仅文本输出 | ✅ 固定流程 | ✅ 自主工具调用 |
| 复杂度 | 低（问答/闲聊） | 中（代码/文档） | 高（科研/自动化） |

### 1.2 Workflows vs Agents 核心区别

根据 Anthropic 2025 年最新研究，必须首先区分两种模式：

| 类型 | 定义 | 控制方 | 适用场景 |
|------|------|--------|----------|
| **Workflows** | LLM 通过预定义代码路径编排 | 开发者控制流程 | 步骤可预测、确定性任务 |
| **Agents** | LLM 动态指导自身流程和工具使用 | LLM 控制流程 | 步骤不可预测、开放式任务 |

**黄金法则**：从最简单方案开始，仅在必要时增加复杂度。

```
└─────────────────────────────────────────────────────────────┘
```

## 三、七大设计原则（优先级排序）

### P0 - 目标唯一性 & 任务边界清晰

**核心**：Agent 只解决**单一领域 / 一类目标**的问题，拒绝「万能 Agent」。

```
❌ 错误示例
"办公全能 Agent" → 能力边界模糊，容易崩溃

✅ 正确示例
"文档总结 Agent" + "PPT生成 Agent" + "数据统计 Agent"
→ 每个 Agent 职责单一，可独立测试和迭代
```

**设计要求**：
- 明确 Agent 的**能力上限与下限**
- 清晰定义**需要人类介入的边界**
- 每个 Agent 任务控制在 **3-10 步**以内

---

### P1 - 最小自主性原则

**核心**：自主性是一把双刃剑——自主性越强，智能度越高，但**可控性越差、出错概率越高、成本越高**。

```
┌─────────────────────────────────────────────┐
│        自主性光谱                              │
│                                              │
│  低自主 ────────────────────────────── 高自主  │
│  │                                        │  │
│  确定性              模糊判断               │  │
│  低风险              高风险                 │  │
│  重复性              创造性                 │  │
│                                              │
│  ✅ Agent 应在此区间运作                     │
│  ❌ 付费/修改数据/高危指令必须人类决策       │
└─────────────────────────────────────────────┘
```

---

### P2 - 可解释性 & 可追溯性

**核心**：Agent 的每一步决策、每一次工具调用，都要能给出**明确理由**。

```
工具调用示例

❌ 无记录
调用了计算器

✅ 有记录
调用计算器 because: "需要计算复杂财务公式，自身算力不足"
```

---

### P3 - 鲁棒性（容错性）

**核心**：Agent 必须能处理异常情况。

```
错误处理流程

工具调用失败
      │
      ▼
  重试 2次
      │
  ├─ 成功 → 继续执行
  │
  ▼
更换工具
      │
  ├─ 成功 → 继续执行
  │
  ▼
求助人类（人机协同）
```

---

### P4 - 效率优先，兼顾精准

**核心**：复杂任务的规划与拆解**不要追求「最优解」，先追求「可行解」**。

---

### P5 - 人机协同闭环

**核心**：永远不要设计「完全自主的 Agent」。

```
核心规则
┌─────────────────┐
│  Agent 提方案   │  ← 模型擅长：分析、推理、生成选项
│    人类做决策    │  ← 人类擅长：判断价值、承担后果
├─────────────────┤
│  Agent 做执行   │  ← 模型擅长：重复性、确定性任务
│    人类做校验    │  ← 人类擅长：质量把控、异常识别
└─────────────────┘
```

---

### P6 - 提示词即代码（Prompt as Code）

**核心**：提示词是"具备版本控制的业务逻辑"，不是临时文本。

**黄金法则**：投入 **50%+** 开发时间在提示工程上。

## 五、记忆系统设计

### 5.1 记忆分层架构

```
┌─────────────────────────────────────────────┐
│              记忆系统三层模型                  │
├─────────────────────────────────────────────┤
│  工作记忆 (Working Memory)                   │
│  ├── 当前对话上下文                          │
│  ├── 近期工具调用结果                        │
│  └── 临时计算中间态                          │
├─────────────────────────────────────────────┤
│  短期记忆 (Short-term Memory)                │
│  ├── 当前会话历史                            │
│  ├── 任务执行轨迹                            │
│  └── 用户当前偏好                            │
├─────────────────────────────────────────────┤
│  长期记忆 (Long-term Memory)                 │
│  ├── 用户画像与偏好                          │
│  ├── 历史任务模式                            │
│  └── 领域知识库                              │
└─────────────────────────────────────────────┘
```

### 5.2 记忆管理最佳实践

- **分离记忆类型**：不要为所有 Agent 使用单一共享记忆
- **上下文窗口管理**：定期压缩和总结历史对话
- **向量检索**：使用嵌入向量实现语义化长期记忆检索
- **状态外置**：将状态存储在数据库/缓存中，支持中断恢复和并行化

## 六、吴恩达四大工程设计范式

### 范式一：反思（Reflection）

Agent 能够**自我审视**输出，发现错误后自我修正。

**实现方式**：
- **单 Agent 自反思**：生成后自我评估
- **双 Agent 协作**：Generator + Critic（通常效果更好）

**适用场景**：写作与内容创作、代码生成、分析与推理任务

---

### 范式二：工具调用（Tool Use）

Agent 能调用外部工具扩展能力边界。

**工具设计原则**：
- 工具即"可执行结构化输出"
- 每个工具本质是一种 JSON 格式的命令
- 使用结构化输出（JSON Schema）确保可靠性
- 文档化工具 thoroughly（ACI 与提示词同等重要）

---

### 范式三：规划（Planning）

Agent 能将复杂任务**分解为可执行的子步骤**。

**规划变体**：
- **静态规划**：一次性规划，按序执行
- **动态规划**：根据结果重新规划
- **层次化规划**：计划中嵌套子计划

**ReAct 框架**：Reasoning（推理）+ Acting（行动）+ Observation（观察）循环

---

### 范式四：多Agent协同（Multi-Agent Collaboration）

多个专业 Agent **分工协作**，各自负责单一领域。

**协作模式**：
- **流水线模式**：顺序执行，各 Agent 处理特定阶段
- **路由模式**：根据输入分类，分发给不同 Agent
- **编排者-工作者**：中央编排器动态分配任务给工作者 Agent
- **辩论模式**：多个 Agent 讨论达成共识

## 七、Anthropic 六大工作流模式

根据 Anthropic 2025 年研究，以下工作流模式按复杂度递增：

### 7.1 Prompt Chaining（提示链）
将任务分解为固定顺序的子任务，每个 LLM 调用处理前一个调用的输出。

### 7.2 Routing（路由）
对输入分类，路由到专用任务或模型处理。

### 7.3 Parallelization（并行化）
将任务分解为可并行执行的独立子任务。

### 7.4 Orchestrator-Workers（编排者-工作者）
中央编排器动态分解任务，分配给工作者 Agent，并综合结果。

### 7.5 Evaluator-Optimizer（评估者-优化者）
一个 Agent 生成输出，另一个 Agent 评估并提供改进反馈。

### 7.6 Autonomous Agent（自主 Agent）
Agent 自主规划、执行、反思，无需人工干预。

## 八、谷歌 5 种 Skill 设计模式

### 8.1 Tool Wrapper（工具包装器）
**内核**：将外部库或团队规范封装为动态加载的 Skill，按需调用。
**适用**：让 Agent 掌握特定库/规范

### 8.2 Generator（生成器）
**内核**：分离"结构"与"内容"，通过模板驱动标准化输出。
**适用**：输出固定格式内容

### 8.3 Reviewer（审查器）
**内核**：模块化检查清单，将审查规则外置到参考文档，动态加载。
**适用**：检查/评审代码或文档

### 8.4 Inversion（反转模式）
**内核**：将"用户驱动Agent"反转为"Agent面试用户"，通过分阶段提问强制需求澄清。
**适用**：需求复杂易误解

### 8.5 Pipeline（流水线模式）
**内核**：用"硬检查点"确保多步骤流程严格有序，禁止跳步。
**适用**：多步骤任务不可跳步

## 九、Self-Improving Agent 自我改进机制

### 9.1 核心理念

**"Correct once, never again"**——用户纠正一次，Agent 永远记住。

### 9.2 三层置信度机制

| 级别 | 信号 | 处理 |
|------|------|------|
| 🔴 HIGH | 显式纠正（"不用 X，用 Y 代替"） | 创建 Critical Corrections |
| 🟡 MEDIUM | 批准（"很好，就是这样"） | 添加到 Best Practices |
| 🟢 LOW | 观察（"你有没有考虑..."） | 记录到 Considerations |

### 9.3 自研发生习循环

```
用户纠正 → 信号检测 → 模式匹配 → Skill 更新 → 永久记忆
    ↑                                              ↓
    └────────────── 下次自动应用 ←──────────────────┘
```

## 十、反模式清单

```
┌─────────────────────────────────────────────────────────────┐
│                      Agent 反模式                           │
├─────────────────────────────────────────────────────────────┤
│  ❌ 万能Agent        一个Agent处理所有任务 → 能力边界模糊    │
│  ❌ 纯自主Agent      无人类介入点 → 错误无法纠正            │
│  ❌ 黑盒Prompt      不可追踪/测试 → 难以调试               │
│  ❌ 硬编码控制流     缺乏灵活性 → 无法应对异常              │
│  ❌ 缺乏错误处理     工具失败即崩溃 → 系统不稳定            │
│  ❌ 无状态设计       每次调用丢失上下文 → 无法连续推理       │
│  ❌ 过度工程化       为简单任务构建复杂系统 → 得不偿失       │
│  ❌ 糟糕提示词       模糊指令、缺少示例 → 性能差             │
│  ❌ 单一共享记忆     所有Agent共用记忆 → 混乱和冲突          │
│  ❌ 隐藏错误         错误不暴露 → 无法调试和改进             │
│  ❌ 缺少评估         无评估标准 → 无法衡量和改进             │
└─────────────────────────────────────────────────────────────┘
```

## 十一、Skill 开发最佳实践

### 评测驱动开发流程

1. **建立基线**：先让模型直接执行任务，记录失败场景
2. **定义评测用例**：优先编写 3-5 个具体用例，明确通过/失败标准
3. **编写最小化 Skill**：只实现通过评测的最短路径
4. **补充边界与示例**：扩展时需新增评测支撑
5. **评测回归与迭代**：每次修改后必须回归测试
6. **真实场景校准**：结合使用反馈形成闭环迭代

### 高命中率 Skill 设计标准

- 精准的元数据（name + description 简洁明确）
- 自由度分级（根据任务复杂度控制约束强度）
- 职责单一、边界清晰、最小必要信息
